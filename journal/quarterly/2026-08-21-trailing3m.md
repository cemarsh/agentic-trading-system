## Structural Problems

**1. The stop-loss module runs on a schedule that does not match intraday price movement.**

*Mechanism:* The stop-loss monitor appears to evaluate positions only at the 13:30 open window (or equivalent batch cycle), not continuously. A CSP can breach its -250% threshold at any point during the session and not be caught until the next evaluation window — by which point it may be at -852%, -900%, or -9,100%. This is not a threshold misconfiguration; it is a monitoring frequency problem. Raising the threshold without fixing the evaluation loop will not change outcomes.

*Evidence:* Three confirmed breaches where realized loss was 3.6× to 36× the configured limit: ABT -900% (W24), KTOS -852% (W26), AADX -9,100% (W27). The W26 wrap-up explicitly raised the question of intraday vs. batch monitoring; it was never answered.

*What must change:* The stop-loss monitor in `position_manager` must run intraday on a sub-5-minute polling loop for any position with beta > 1.0, or implement exchange-native stop orders at entry so enforcement is not dependent on the monitoring loop at all. Until this is confirmed operational, no CSP should be opened on any name with beta > 1.0.

---

**2. The wheel engine and position_manager do not share position state.**

*Mechanism:* The wheel engine evaluates opening candidates against a static universe list. The position_manager evaluates open positions for closure or rolling against a separate ledger. Neither queries the other before acting. The result is that the wheel engine opens a new CSP on ticker X in the AM cycle while the position_manager is simultaneously closing or rolling an existing CSP on ticker X from a prior session. The cost is: full premium paid on the BTC plus bid-ask on the new open, with zero net income.

*Evidence:* W24 (ABT opened and stopped same session), W26 (six names simultaneously managed by both engines on 6/22, ALB opened and BTCed same session on 6/26), W27 (AM and PM double-fire generating ~$1,061 in BTC losses). The sequencing failure was named explicitly in the W26 weekly wrap-up. No fix was committed at any point in the quarter.

*What must change:* The wheel engine must query a shared position ledger before generating any new entry signal. The ledger must be the single source of truth — if `position_ledger.get(ticker)` returns an open record, the wheel engine must skip that ticker unconditionally. The v2.1 risk engine introduced a position ledger; it must be wired as a blocking gate into the wheel's candidate-selection step, not just into post-trade accounting.

**3. Policy signals have no execution pathway.**

*Mechanism:* The policy monitor fires at L1 confidence ≥ 0.85, logs `status: SIGNAL`, and terminates. There is no downstream code that converts the signal into an order object, routes it to the broker API, or even flags it for manual review with a time limit. The signal-to-order bridge does not exist. This is not a signal quality problem — the signals on PLTR, LHX, RTX, LDOS were directionally correct and would have been profitable. The system is simply not wired to act on them.

*Evidence:* Zero policy-driven trades across all 6 weeks with confirmed signal data (W23–W27, W29–W31). 90+ signals logged in W29–W31 alone, zero executed. The gap was named in W29, W30, W31 monthly summaries without remediation.

*What must change:* A `policy_signal_executor` module must be built (or wired if already partially built) that takes a confirmed L1 signal, looks up the ticker in the wheel universe or a separate policy-trade universe, checks current position state via the shared ledger, sizes a position per the risk engine's pre-trade gates, and submits a limit order. Until this exists, the policy monitor is a logging service with no trading function and should not be described as part of the trading system.

## What Needs To Be Worked On

**1. Fix intraday stop-loss enforcement for all open positions — `position_manager`, monitoring loop frequency.**

The current batch-window evaluation is the proximate cause of the three worst single-trade losses this quarter (-$852%, -$900%, -$9,100% against a -250% threshold). Replace the batch stop-loss check with either: (a) a continuous sub-5-minute polling loop for positions with beta > 1.0, or (b) native stop orders submitted to the broker at the time of entry so enforcement is exchange-side and does not depend on the monitoring loop. Implement `equity_max_loss_pct` for long equity positions at the same time. Measure by: zero future stop breaches exceeding 1.5× the configured threshold in backtesting and live paper trading. Expected effect: recovers an estimated $3,000–$6,000 per quarter in losses that currently run past configured limits.

**2. Wire the shared position ledger as a blocking gate in the wheel engine's candidate-selection step — `wheel_engine`, candidate filter, v2.1 position ledger.**

The double-fire open/close pattern cost approximately $1,061 in a single week (W27) and occurred in at least four separate documented instances. The ledger exists in v2.1; it is not being queried before new entries are generated. Add a single ledger lookup at the start of `wheel_engine.get_candidates()`: if `position_ledger.get(ticker).status == OPEN`, remove the ticker from candidates unconditionally. Measure by: zero same-session open/close events in post-trade logs. Expected effect: eliminates a confirmed recurring loss source, recovers $100–$500 per event, and prevents the wheel engine from compounding losses on already-underwater names (KTOS re-entries).

**3. Build the policy signal execution pathway — new module `policy_signal_executor`, wired downstream of `policy_monitor`.**

The policy monitor is generating correct L1 signals and stopping. No code routes those signals to orders. This is the largest lost-opportunity cost in the system: 90+ signals across 6 weeks, zero executed, on names (PLTR, RTX, LHX, LDOS) that moved in the signaled direction. Build `policy_signal_executor` to: receive a confirmed L1 signal, query the position ledger, size via the risk engine's pre-trade gates, and submit a limit order. Initial scope can be equity entries only (simpler than CSPs). Measure by: at least one policy-driven trade executed per week when L1 signals fire. Expected effect: converts the system's strongest signal source from zero revenue to positive expectancy — the June wrap-up described signal quality as sufficient; the failure is purely architectural.

**4. Define and enforce `equity_max_loss_pct` for FJET immediately, and resolve the share-encumbrance accounting bug — `position_manager`, position schema.**

FJET has lost an estimated $9,745 unrealized against a position that has had no stop for 7 weeks. This is the single largest current drag. Set `equity_max_loss_pct = -0.15` in the position schema and confirm the position_manager evaluates it on the same loop as CSP stops. Separately, diagnose and fix the share-encumbrance accounting bug that locked 93% of FJET shares — this prevented covered-call mitigation for the entire month of July. Measure by: position closed or hedged within the current week; covered-call capability confirmed in paper trade log. Expected effect: stops active drawdown accumulation on the account's largest unrealized loss.

**5. Correct the sector-mapping table in `policy_monitor` and add a misfire guard.**

Five documented misfires in 2 months. The table is wrong in a systematic way (AI-infra tickers returned for unrelated policies). Audit every ticker-to-sector mapping, remove any ticker whose connection to a sector cannot be documented with a specific rationale, and add a misfire guard that flags any signal where the returned tickers have no semantic overlap with the policy's named industry. Run the corrected classifier against 30 historical EOs before re-enabling. Measure by: zero misfires in the subsequent month's signal log. Expected effect: prevents a future session from trading on a bad signal, and improves signal precision enough that the executor built in item 3 can operate with less human review overhead.

**6. Add `secondary_csp_watchlist` to wheel engine config and wire research-layer IVR output as a direct input — `wheel_engine`, config, NotebookLM pipeline.**

The system was idle for multi-week stretches while AVAV, CAT, VST, and CEG showed IVR of 51–100% and were not traded. The research pipeline identified all of them; the wheel engine never saw the output. Populate `secondary_csp_watchlist` with 8–12 pre-approved, non-earnings-correlated tickers. Add a pipeline step that writes the research layer's IVR scores to a shared file or database table that the wheel engine reads during candidate scoring. Measure by: at least one secondary-watchlist trade executed during the next earnings-cluster blackout period. Expected effect: eliminates multi-week idle stretches and begins deploying the 79.8% idle cash balance in a controlled, pre-approved way.

**7. Fix the wheel engine loop deduplication bug — `wheel_engine`, skip-decision logging.**

The skip-decision log fires 150–320 times per ticker per session, generating 1,400–1,755 log entries per day and burying real decision events. This is confirmed in W29, W30, W31. Locate the loop that calls the skip-decision logger and add a per-ticker session-scoped deduplication guard (a set cleared at session open). Measure by: skip-decision log count ≤ 1 per ticker per session in the following week's log analysis. Expected effect: makes the insight log readable, which is a prerequisite for diagnosing the other bugs on this list — the noise is currently obscuring whether fixes in items 1–6 are actually running.
