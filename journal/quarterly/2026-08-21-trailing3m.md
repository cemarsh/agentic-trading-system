## Structural Problems

**1. FJET has no exit architecture — and the problem is generic, not ticker-specific.**
The mechanism: the system can enter equity positions (FJET, MSFT) but has no enforced stop-loss, covered-call trigger, or maximum holding-loss rule for equity longs. FJET deteriorated from −8% to −41% over six weeks with zero automated response. The quarantine gate correctly blocked *new* CSPs but did nothing about the existing long. The covered-call pathway exists conceptually but was blocked by a position encumbrance accounting error (309 of 4,570 shares listed as available) that was never diagnosed or corrected. What would have to change: (a) implement `max_equity_drawdown_pct` as a hard exit rule in `position_manager` for all equity longs, not just options; (b) audit and fix the share-availability accounting so covered calls can be written against the full long position; (c) add a weekly forced-review gate that requires a documented decision (hold/hedge/exit) for any equity position beyond −10% unrealized.

**2. The stop-loss monitor is not running intraday on short puts.**
The mechanism: KTOS was sold as a short put at $2.10 premium and marked to $20.00 before the stop triggered — a −852% loss against a −250% threshold. This means the monitor checked the position at most once daily, after the damage was done. Short puts on high-beta names (KTOS, PLTR, RKLB) can move from −50% to −500% intraday on a gap. A once-daily check is structurally incompatible with short-premium risk management on volatile underlyings. What would have to change: `position_manager` stop-loss monitor must poll short-put marks intraday (minimum every 30 minutes during market hours); set a separate, tighter stop threshold for names with beta > 1.5 (`stop_loss_pct_high_beta = -150%` vs. the current `-250%` generic threshold); add a `max_loss_per_position` dollar cap independent of percentage.

**3. The wheel engine has no shared state with the position ledger, causing contradictory and self-defeating behavior.**
The mechanism: in W26, the wheel fired six new SELL_PUT orders on the same morning that position_manager submitted BTC and roll orders on the same tickers. In W26 and W27, positions were opened and closed same-session (ALB, XOM). In W27, the wheel fired AM and PM cycles on the same day on the same names. The wheel engine is reading the opportunity set from a universe list, not from a live position ledger, so it does not know the book is already stressed. What would have to change: the wheel engine must query the position ledger before generating any new SELL_PUT signal and gate on (a) existing unrealized loss > X% in the same ticker, (b) total book unrealized loss > Y% of equity, and (c) sector concentration thresholds already breached. The `position_ledger` module from v2.1 is the right integration point — wire the wheel's candidate filter to it.

**4. Policy signals have no execution pathway — the module is a logger, not a trader.**
The mechanism: the policy monitor consistently fires at conviction 0.85, Level 1, with named tickers and sector mappings. Across at least three full weeks (W30, W31, W32) — representing 90+ distinct signal events — zero converted to orders. The `status: SIGNAL` state is a terminal state; there is no downstream logic to evaluate whether a signal meets entry criteria and submit an order. The classifier also has a confirmed sector-mapping bug (AI-infra tickers returned for aviation, agricultural, and beverage policy) that inflates false-positive rates and will eventually produce a bad trade if execution is ever wired up. What would have to change: (a) implement a signal-to-order handler that evaluates each policy signal against IV rank, position ledger capacity, and sector cap before submitting; (b) fix the sector-mapping model — at minimum, audit the mappings for the five most-misclassified policy categories (aviation, agricultural, automotive, chemical, monument) before enabling live execution; (c) add signal deduplication so the same EO does not fire twice in the same session.

**5. The wheel scanner has no in-session deduplication, making the log unauditable.**
The mechanism: the scanner runs on a tight loop (every 60–65 seconds) with no in-memory guard against logging the same skip decision repeatedly. Result: 100–300 identical log entries per session, 1,400–1,755 "insights" per day that are overwhelmingly noise. This was first documented in W27 (six weeks ago) and is still present in W32 with no remediation commit. The consequence beyond log pollution is that genuine decision events — actual entries, exits, blocks for substantive reasons — are buried and cannot be reliably extracted for post-trade analysis. What would have to change: add a `last_logged_decision` hash per ticker per session in the scanner's in-memory state; only log a skip event once per ticker per session unless the underlying reason changes. This is a one-day engineering fix that has been deferred for six weeks.

**6. Strike selection on short puts has no systematic floor relative to realized volatility.**
The mechanism: CCJ puts were sold at strikes ($90, $98) on a uranium name that moved sufficiently to make both ITM, requiring BTC at loss. AADX was sold at a $0.05 premium — a name with no pre-trade analysis and sufficient tail risk to produce a −9,100% stop (−$455 loss on negligible premium). MP went −119.6% (−$324). The common pattern: strikes are selected too close to spot, or premium is too thin relative to the underlying's realized move potential. The system has an IV rank gate but no realized-volatility filter and no minimum expected-value calculation before entry. What would have to change: add a `min_expected_value` pre-trade check in the wheel engine: `(premium collected) / (max loss at stop threshold) > configurable_ratio` (suggest 0.15 minimum); add a `min_otm_pct` floor scaled to the underlying's 30-day realized vol (e.g., strike must be ≥ 1.0× realized vol OTM); prohibit CSP entries where premium < $0.50/share on any name regardless of IVR.
